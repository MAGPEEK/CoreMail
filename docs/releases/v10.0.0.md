# CoreMail v10.0.0: room and equipment resources removed

**Image:** `magpeek/coremail-app:10.0.0` · **Helm chart:** 3.0.0 · **Date:** 2026-11-19 · **Predecessor:** v9.5.1

This is a major release: room and equipment resources are removed completely, like distribution groups in v5.6.1 and public folders in v3.18.31. Nothing else changes. Please read the upgrade steps before you upgrade from 9.5.x — room data is deleted at start, after a mandatory backup.

## What was removed

- **Room and equipment mailboxes** with their booking rules, bookings, automatic accept / decline and iMIP replies, and the rooms' own mailboxes.
- **Admin API** `/api/v1/admin/resources` (incl. bookings and free/busy), EMS `GET /api/v1/admin/ems/resource-mailboxes` and `GET /api/v1/calendar/rooms` — all answer 404. The `rooms` field of `POST` / `PUT /api/v1/calendar/events` and the `rooms` / `uid` fields of `POST /api/v1/calendar/schedule-suggestions` are ignored when sent; the organisation GAL has no `resources` key.
- **Webmail:** the room picker of the event form and the room rows of the scheduling assistant. **ActiveSync:** room booking of meetings written by a phone. **SMTP:** the recipient lookup of room addresses.

Every attendee — also one another client marks as `CUTYPE=ROOM` / `RESOURCE` — is now stored and invited like a person.

## Why the upgrade is safe

- schema-sync drops only the three retired tables (`resource_mailboxes`, `resource_calendars`, `resource_bookings`) and the rooms' own owner-less mailboxes — and only **after** a mandatory pg_dump to `/data/backups` succeeded. The log lists every table with its row count.
- Any other data loss is still refused: if a different destructive change shows up next to the room tables, nothing is changed.
- If the dump cannot be written, the start stops before anything is deleted.
- The e2e step `schema-upgrade` upgrades a 9.5.x database with room rows and checks that the dump is written first, only the rooms' own mailboxes are deleted and all other data is kept.

## Upgrade

```bash
cd /opt/coremail && git pull && docker compose pull && docker compose up -d
```

1. **Room data is deleted after a backup.** With room rows present, the first start writes `/data/backups/pre-migrate-<UTC timestamp>.sql.gz` and then drops the room tables and the rooms' own mailboxes (folders, messages, attachments). No `COREMAIL_ALLOW_SCHEMA_DATA_LOSS` is needed. If the dump fails (no space, PostgreSQL newer than the image's `pg_dump`, directory not writable), make your own backup and start once with `COREMAIL_SCHEMA_BACKUP=skip`.
2. **Helm:** set `app.schemaSync.backupClaim` (or `app.schemaSync.skipBackup=true` after your own backup) for this rollout when room rows exist; otherwise the init container stops without changes. See "Upgrading to chart 3.0" in `infra/k8s/README.md`.
3. **Mail to former room addresses is refused** with `550 5.1.1` at RCPT; local senders get an NDR. Remove rooms from existing meetings — otherwise later updates or cancellations sent to them bounce to the organizer.
4. **Recreate bookable rooms** as a **shared mailbox** whose calendar is shared with the people who book it, or as a **shared calendar** per room, and check availability with the scheduling assistant / free-busy.
5. Clients of the removed APIs get 404.

## Notes

- Raw messages and attachment files of the deleted room mailboxes stay in the object store without any row pointing at them: no API serves them, they only take space and are in no backup.
- A mailbox row left behind by a room deleted in 9.x is not touched.
- A queued 9.5 room reply that is still in the outbound queue is delivered without sender authentication.
- Webmail event form: the location placeholder now reads "Ort hinzufügen".

# CoreMail v10.4.1: no init container

**Image:** `magpeek/coremail-app:10.4.1` · **Helm chart:** 3.4.0 · **Date:** 2026-11-20 · **Predecessor:** v10.4.0

A patch release for the deployment: the separate one-shot container `coremail-init` is gone. The main container `coremail` creates the secrets in `./secrets/` and prepares the configuration itself on its first start; PostgreSQL, Redis and the optional services wait briefly for their password files and then start as usual.

## New installation

```bash
mkdir coremail && cd coremail
curl -fsSLO https://github.com/MAGPEEK/CoreMail/releases/latest/download/docker-compose.yml
docker compose up -d
```

Then open `http://<server>:3000/setup` with the token from `./secrets/setup-token`.

## Update from 10.4.0

```bash
curl -fsSLO https://github.com/MAGPEEK/CoreMail/releases/latest/download/docker-compose.yml
docker compose pull && docker compose up -d --remove-orphans
```

`--remove-orphans` removes the old, exited `coremail-init` container. Secrets and data stay unchanged.

## `docker run`

The image no longer has the standalone commands `coremail-init`, `coremail-init-secrets` and `coremail-init-config`; their work is done only by the entrypoint of the `coremail` container. Without Compose, start the `coremail` container first (with `./secrets` mounted at `/secrets`); PostgreSQL and Redis wait in a small `sh -c` loop until their password file exists. The commands: [deploy.md → docker run](../deploy.md#docker-run).

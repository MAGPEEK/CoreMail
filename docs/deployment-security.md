# CoreMail — Deployment security

Hardening of the Docker / Kubernetes deployment, the configuration and the
backup layer. Everything here is on by default for new installations
(`scripts/setup.sh`, `scripts/synology-setup.sh`); existing installations keep
working and can opt in step by step (each section says how).

## 1. New and changed environment variables

| Variable | Where | Default | Meaning |
|---|---|---|---|
| `BACKUP_ENCRYPTION_KEY` | app | derived from `JWT_SECRET` + `PEPPER` (warning) | 32-byte key (64 hex chars or base64) for backup encryption. Generated by `setup.sh`. **Keep a copy off the server.** An invalid value makes every backup fail (never plaintext). |
| `COREMAIL_ALLOW_SCHEMA_DATA_LOSS` | app | `false` | `true` allows ONE destructive schema update, after a `pg_dump`. |
| `COREMAIL_SCHEMA_BACKUP_DIR` | app | `/data/backups` | Where that dump goes (volume `coremail-data`). |
| `COREMAIL_SCHEMA_BACKUP` | app | `required` | `skip` = no automatic dump (you made your own backup). |
| `COREMAIL_DB_USER` / `COREMAIL_DB_PASSWORD` | app + postgres | unset (= superuser `coremail`) | Least-privilege application role. `setup.sh` sets them for a **fresh** database. |
| `RSPAMD_CONTROLLER_PASSWORD` | rspamd | empty | Password of the rspamd web UI / API for every address except the app. Generated by `setup.sh`. |
| `RSPAMD_NET_PREFIX` | compose | `10.253.253` | `/29` of the dedicated app ↔ rspamd network (app `.2`, rspamd `.3`). Change only on a subnet collision. |
| `MINIO_ACCESS_KEY` / `MINIO_SECRET_KEY` | app | **no default any more** | Required for `OBJECT_STORAGE=minio|s3` (Compose sets them from `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`). |
| `S3_ACCESS_KEY` / `S3_SECRET_KEY` | app (backups) | **no default any more** | Backup bucket credentials (Compose sets them). |

Helm values: `app.schemaSync.allowDataLoss`, `app.schemaSync.backupClaim`,
`app.schemaSync.skipBackup` (see `infra/k8s/README.md`).

`scripts/setup.sh` only ever **adds missing** keys to `.env`; it never changes
an existing value. Re-run it after an upgrade to get the new secrets.

## 2. Database schema updates fail closed

At every start the app container (and the Helm `schema-sync` init container)
runs `coremail-schema-sync` (`infra/docker/schema-sync.sh`):

1. `prisma db push` **without** `--accept-data-loss` (retried while PostgreSQL
   is still starting).
2. If the new schema would delete data (dropped table/column that still has
   rows, narrowed type …) the start **stops**, nothing is changed, and the log
   says what to do. Before, such changes were applied silently.
3. To apply it: back up, set `COREMAIL_ALLOW_SCHEMA_DATA_LOSS=true` in `.env`,
   `docker compose up -d coremail`. CoreMail first writes
   `/data/backups/pre-migrate-<UTC timestamp>.sql.gz` (`pg_dump`, plain SQL,
   gzip, mode 0600) and only after that succeeded runs the push with
   `--accept-data-loss`. **Remove the setting again afterwards.**
4. Changes Prisma cannot execute at all (e.g. a new required column without a
   default on a non-empty table) always stop the start — manual migration.

The dump lives on the `coremail-data` volume:

```bash
docker run --rm -v coremail_coremail-data:/data alpine ls -l /data/backups
# restore (stack stopped except postgres):
docker run --rm -v coremail_coremail-data:/data alpine cat /data/backups/pre-migrate-<ts>.sql.gz \
  | gunzip | docker exec -i coremail-postgres psql -U coremail -d coremail
```

The image contains `pg_dump` 16 (`postgresql16-client`), matching the bundled
`postgres:16`. With a newer external PostgreSQL `pg_dump` refuses — back up
yourself and set `COREMAIL_SCHEMA_BACKUP=skip`.

## 3. Database role (no superuser)

Before, the app connected as `POSTGRES_USER=coremail`, a PostgreSQL superuser
(file access via `COPY … PROGRAM`, other databases, roles …).

**New installations** (`setup.sh` / `synology-setup.sh` on an empty database
volume) set `COREMAIL_DB_USER=coremail_app` + a random `COREMAIL_DB_PASSWORD`.
On the first start of the empty volume `infra/docker/postgres/02-app-role.sh`
creates that role: `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE`, `CONNECT` +
`TEMPORARY` on the database, **owner of schema `public`** (Prisma creates and
alters the tables as it). `coremail` stays the administrative superuser
(`pg_dump`, `psql`, the healthcheck).

> The init script only runs on an **empty** data volume. Setting
> `COREMAIL_DB_USER` for an existing database without the steps below makes the
> login fail (`password authentication failed for user "coremail_app"`).

**Existing installations** (optional):

```bash
# 1. backup first
docker exec coremail-postgres pg_dump -U coremail coremail | gzip > coremail-$(date +%F).sql.gz
# 2. password into .env
echo "COREMAIL_DB_USER=coremail_app"              >> .env
echo "COREMAIL_DB_PASSWORD=$(openssl rand -hex 20)" >> .env
# 3. create the role and hand over the schema (one transaction)
. ./.env
docker exec -i coremail-postgres psql -U coremail -d coremail \
  -v app_password="$COREMAIL_DB_PASSWORD" < infra/docker/postgres/migrate-to-app-role.sql
# 4. restart the app with the new DATABASE_URL
docker compose -f infra/docker/docker-compose.yml up -d coremail
```

Rollback: remove the two lines from `.env` and `up -d coremail` — the superuser
still owns everything it needs.

Restoring a dump into a role-based installation: restore **as the app role** so
it owns the objects:
`gunzip -c dump.sql.gz | docker exec -i coremail-postgres psql -U coremail_app -d coremail`
(local socket connections inside the container need no password). Restored as
`coremail` instead, run `migrate-to-app-role.sql` again without the
`CREATE ROLE` line.

Kubernetes: the chart's bundled PostgreSQL is unchanged (the app uses
`postgresql.auth.username`); with an external database create a non-superuser
owner yourself.

## 4. Encrypted backups

The backup-service (full backups, mailbox backups, schedules) encrypts every
archive **inside the container** before it is uploaded to the backup bucket.

- Algorithm: AES-256-GCM in 64 KiB frames (streaming — any size). Per file a
  random 16-byte salt; the file key is HKDF-SHA256(master key, salt). Nonce =
  frame counter + "final frame" flag, so modified, reordered, dropped or
  truncated frames are detected. The header (format version, frame size, salt,
  key id) is authenticated with every frame.
- Objects are stored as `<name>.zip.enc` / `<name>.mbox.enc`
  (`Content-Type: application/octet-stream`, metadata
  `x-amz-meta-encryption: coremail-aes-256-gcm-v1`). The plaintext temp file in
  the container is deleted even when the upload fails.
- **Download** (BCP → Backup & Restore, `/backup/admin/download/:jobId`,
  `/backup/admin/archive/download?key=`): decrypted on the fly; the browser gets
  the original `.zip`/`.mbox`. A wrong key or a foreign file is answered with an
  error before any byte is sent; a corrupted frame aborts the transfer.
- **Import** (`POST /backup/admin/import/:userId?folderId=<id>`, body
  `application/mbox` or `application/octet-stream`): accepts an encrypted
  `.mbox.enc` as well as a plaintext MBOX (old backups, exports from other
  systems). Encrypted input is fully decrypted **and authenticated** before the
  first message is imported (tampered → HTTP 422, nothing imported). Note: the
  target folder is now taken from the query string.
- Backups made before this change stay plaintext objects and download as before.

### Key

`BACKUP_ENCRYPTION_KEY` — 64 hex characters (`openssl rand -hex 32`) or base64 of
32 bytes. Without it the key is derived from `JWT_SECRET` + `PEPPER` and a
warning is logged at every start: rotating either secret would then make the
backups unreadable. The service always also accepts the derived key when
decrypting, so backups written before you set `BACKUP_ENCRYPTION_KEY` stay
readable. The log shows the key id in use
(`Backup encryption enabled … keyId`), every file header carries it.

**Store the key off the server** (password manager / safe). Lose the server and
the key — and the backups are gone. Rotating the key: older backups need the old
key; decrypt them with the script below (or keep the old key until they expire).

### Disaster recovery without CoreMail

`scripts/decrypt-backup.mjs` (Node 18+, no dependencies) decrypts an object
downloaded straight from the bucket:

```bash
BACKUP_ENCRYPTION_KEY=<64 hex> node scripts/decrypt-backup.mjs a_at_b.zip.enc a_at_b.zip
# installations without BACKUP_ENCRYPTION_KEY (derived key):
JWT_SECRET=… PEPPER=… node scripts/decrypt-backup.mjs 123.mbox.enc 123.mbox
```

It verifies every frame and deletes the partial output on any error.

## 5. Container hardening (docker-compose.yml)

The `coremail` service runs with

```yaml
security_opt: [no-new-privileges:true]
cap_drop: [ALL]
cap_add: [CHOWN, DAC_OVERRIDE, FOWNER, SETUID, SETGID, KILL, NET_BIND_SERVICE]
sysctls: { net.ipv4.ip_unprivileged_port_start: 0 }
```

Why each capability is needed (all used by root processes only — the services
themselves run as `node` without capabilities):

| Capability | Used by |
|---|---|
| `CHOWN`, `FOWNER` | entrypoint: hand the storage directory to `node` (bind mounts, old volumes), `chmod` it |
| `DAC_OVERRIDE` | entrypoint/supervisord as root writing into `node`-owned directories (`/data`, supervisor logs), the pre-migration dump |
| `SETUID`, `SETGID` | supervisord switches every program to `user=node` |
| `KILL` | supervisord (root) stops/restarts programs running as `node` |
| `NET_BIND_SERVICE` | must stay in the bounding set: the `node` binary carries the file capability `cap_net_bind_service`, and exec of such a binary fails with EPERM when the capability is not in the bounding set |

With `no-new-privileges` the file capability of `node` is not granted any more,
so binding ports 25/110/143/443/465/587/993/995 works through the
namespaced sysctl `net.ipv4.ip_unprivileged_port_start=0` (only inside the
container's network namespace). Verified with the e2e suite (all checks pass).
The root filesystem stays writable (not verified read-only for Compose; the Helm
chart already runs read-only).

Not applied to `docker-compose.synology.yml` (DSM's Docker was not tested).

## 6. rspamd controller

The controller (port 11334: scanning, Bayes learning, stats) previously trusted
**every RFC 1918 address** without a password. Now
(`infra/docker/rspamd/local.d/worker-controller.inc`):

- rspamd sits on its own network `rspamd` (`${RSPAMD_NET_PREFIX}.0/29`) with
  only the app container; app = `.2`, rspamd = `.3` (both fixed).
- `secure_ip` = `127.0.0.1`, `::1` and the app's address (env
  `RSPAMD_CONTROLLER_SECURE_IP`). Without that env: loopback only (fail closed).
- Everything else needs `RSPAMD_CONTROLLER_PASSWORD` (also for the web UI:
  `docker exec -it coremail-rspamd …` or an SSH tunnel; the port is not
  published). Empty password = no access except from `secure_ip`.

CoreMail itself does not send a controller password yet, which is why the app
address must stay in `secure_ip`.

If `10.253.253.0/29` collides with a network on the host or LAN, set e.g.
`RSPAMD_NET_PREFIX=10.99.42` in `.env` (the e2e override uses `10.253.254`).

## 7. No default credentials

- `OBJECT_STORAGE=minio|s3` without `MINIO_ACCESS_KEY` + `MINIO_SECRET_KEY` is a
  configuration error (`ObjectStorageConfigError`), no silent
  `minioadmin/minioadmin`.
- The backup bucket without `S3_ACCESS_KEY` + `S3_SECRET_KEY`: the
  backup-service starts (mail keeps working) but logs the error and every backup
  run fails.
- `docker-compose.synology.yml` no longer contains fallback passwords
  (`CoreMail2024!`, `RedisSecret2024`, `MinioSecret2024!`,
  `CHANGE-ME-…`); every secret is `${VAR:?…}`.
- Every service warns at start when `JWT_SECRET`, `PEPPER`,
  `MFA_ENCRYPTION_KEY` or `BACKUP_ENCRYPTION_KEY` still contains a `CHANGE-ME`
  placeholder.

## 8. Log redaction

The shared pino logger (`@coremail/core`) replaces these values with
`[Redacted]`: `authorization`, `cookie`, `set-cookie`, `password`,
`currentPassword`, `newPassword`, `appPassword`, `token`, `accessToken`,
`refreshToken`, `challengeToken`, `secret`, `clientSecret` — at the top level of
a log object and one level below (`*.password`), plus `req.headers.*` /
`res.headers.set-cookie` / `headers.*` (authorization, cookie, x-internal-token).

## 9. Synology: secrets and rotating the old default passwords

`scripts/synology-setup.sh` now writes every secret into
`/volume1/docker/coremail/.env` (chmod 600) and copies the PostgreSQL init and
rspamd configuration to `/volume1/docker/coremail/config/`.

- **Fresh installation:** all secrets random, plus the database role (§3).
- **Existing installation** that ran on the old Compose fallbacks: the old
  values are written explicitly (so nothing breaks) and listed as a warning —
  **except `JWT_SECRET`**: a publicly known JWT secret lets anyone forge login
  tokens, so it is rotated right away. Its only other use was deriving the 2FA
  (TOTP) encryption key; that key is pinned first as `MFA_ENCRYPTION_KEY`
  (same bytes), so existing 2FA keeps working. Every user is logged out once.

Rotating the remaining old defaults:

| Secret | How |
|---|---|
| `POSTGRES_PASSWORD` | `docker exec -it coremail-postgres psql -U coremail -c "ALTER USER coremail PASSWORD '<new>'"`, put `<new>` into `.env`, `docker compose up -d` |
| `MINIO_ROOT_PASSWORD` | new value in `.env`, `docker compose up -d minio coremail` (MinIO reads the root credentials from the environment) |
| `PEPPER` | **cannot be rotated** without resetting every password (it is part of every hash). Keep it secret from now on; strong user passwords and MFA matter more here. |

## 10. Signed images (CI)

`.github/workflows/docker-publish.yml` builds the shipped image
`magpeek/coremail-app` from `infra/docker/Dockerfile.app` (amd64 + arm64) with
SLSA provenance (`mode=max`) and an SBOM attached as registry attestations,
then signs the digest with cosign (keyless, GitHub OIDC). Actions are pinned by
commit SHA; the job has only `contents: read` and `id-token: write`.

```bash
cosign verify docker.io/magpeek/coremail-app:<version> \
  --certificate-identity-regexp '^https://github.com/MAGPEEK/CoreMail/\.github/workflows/docker-publish\.yml@refs/(heads/main|tags/v.*)$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
docker buildx imagetools inspect docker.io/magpeek/coremail-app:<version> --format '{{ json .SBOM }}'
```

The old per-service images (`magpeek/coremail-<service>`) are no longer built.
